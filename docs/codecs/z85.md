# z85

6.4 bits per character: {doc}`base85` with ZeroMQ's alphabet, which trades
base85's backquote, semicolon, pipe, underscore and tilde for `.`, `:`, `/`,
`[` and `]`, decoded strictly.

The same five characters per four bytes and the same tail rule as base85,
over the 85 characters `0` to `9`, `a` to `z`, `A` to `Z` and
`.-:+=^!/*?&<>()[]{}@%$#`. Like base85 it has no quotes and no backslash,
so the text sits inside a JSON string or a quoted string literal without
escaping; unlike base85 it also has no backquote, `;`, `|`, `_` or `~`. It
is not shell-safe: unquoted, `*`, `?`, `&`, `<`, `>`, `(`, `[`, `{`, `$` and
`#` are the shell's, and inside double quotes `$(` still opens a command
substitution. Pass it in single quotes, which the alphabet never breaks, or
through a variable. The characters are the standard library's `z85encode`
output (3.13 and later), returned as `str`, and the decoder takes the same
strict reading as base85: one payload, one spelling.

ZeroMQ's specification defines Z85 for payloads that are a multiple of four
bytes. This codec takes any length, with the standard library's tail
convention, so `z85.encode(b"hi")` works; a consumer that follows the
specification to the letter expects padded input.

## When to use it

100 characters hold 80 bytes, the same as base85. Pick z85 over base85 when
the text goes through a channel that treats backquote, `|`, `;`, `_` or `~`
specially: Markdown and shell-adjacent formats, identifiers with underscore
rules, columns split on pipes. ZeroMQ uses it for
CurveZMQ keys, which is where most z85 text in the wild comes from. Inside
a URL it still needs percent-encoding for `/`, `?`, `&`, `#` and `%`;
{doc}`base64url` is the codec for that channel.

It does not save bytes: as UTF-8 each character costs one, so the text is
five characters for every four bytes, a quarter longer than the payload.

## Truncation behavior

The same as base85: a cut inside a group of five raises
{class}`~radixly.DecodeError` unless the cut tail happens to be an exact
spelling, a cut on a group boundary passes and decodes to a prefix of the
payload. About three cuts in ten pass; there is no length and no checksum
to catch them.

```python
from radixly import z85

payload = bytes(range(20))
text = z85.encode(payload)             # 25 characters
z85.decode(text[:10]) == payload[:8]   # True
```

If a shortened string must be caught, carry a length or checksum alongside
it, or use {doc}`uro14`, whose length prefix rejects every truncation below
its 16,384-byte window.

## Standard library

`radixly.compat.base64.z85encode` and `z85decode` port the standard
library's functions, lenient tail included, onto this codec's C, on the
interpreters that have them. See {doc}`../compat`.
