# base65536

16 bits per character: every pair of bytes becomes one code point.

[qntm's base65536](https://github.com/qntm/base65536) takes the idea behind
base32768 to its limit for channels that count code points: two bytes per
character, from 256 blocks of 256 consecutive code points each. The second
byte of a pair picks the block, the first the offset inside it. A final odd
byte gets a character from a 257th block of its own, so nothing ever needs
padding and `n` bytes become `ceil(n / 2)` characters. radixly's encoder
matches the reference implementation byte for byte on qntm's published test
vectors.

Most of the blocks lie outside the Basic Multilingual Plane, among them CJK
ideographs from the supplementary planes, Linear A, cuneiform, hieroglyphs
and Bamum. Each such character is a surrogate pair in UTF-16, so a channel
that counts code units sees half the density. Twitter is a different story:
since 2017 it counts every code point from U+1100 upward as two, the rule
{doc}`base2048` was built around and the reason qntm retired base65536 there.

## When to use it

100 code points hold 200 bytes, the most of any codec here. If your channel
counts code points and accepts the supplementary planes, nothing beats it. It
was designed for exactly that: a limit expressed in characters, with no
opinion about which characters.

Every code point is assigned, non-combining, and stable under all four
Unicode normalization forms, and the text contains no whitespace or control
characters. What it does not survive is a channel that counts UTF-16 code
units, or one that strips astral characters: there, {doc}`base32768` is the
safer choice.

It does not save bytes: as UTF-8 most characters cost four.

## Truncation behavior

What happens when an encoded string loses characters at its end and you
decode what is left?

Every prefix of a base65536 string is itself a valid base65536 string. Cut
one after `k` characters and it decodes, without an error, to the first
`2 * k` bytes of the payload. There is no padding, no length and no
checksum, so the decoder has nothing to object to. Measured over random
payloads and every cut position, 100% of truncated strings decode, all of
them to a prefix.

```python
from radixly import base65536

payload = bytes(range(20))
text = base65536.encode(payload)            # 10 characters
base65536.decode(text[:8]) == payload[:16]  # True, always
```

If a shortened string must be caught, carry a length or checksum alongside
it, or use {doc}`uro14`, whose length prefix rejects every truncation below
its 16,384-byte window.
