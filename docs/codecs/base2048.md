# base2048

11 bits per character from 2,048 code points below U+1100, decoded strictly
and canonically.

[qntm's base2048](https://github.com/qntm/base2048) was built for a channel
with a twist: Twitter counts code points, but every code point from U+1100
upward counts double. base2048 stays below that line, so each character
counts once and carries 11 bits. Its alphabet is letters and digits from the
Latin, Greek, Cyrillic, Armenian, Hebrew, Arabic and Indic scripts, among
others. A leftover of 1 to 3 bits at the end goes into a short character
from a second alphabet of 8, a leftover of 4 to 10 into a padded 11-bit
character, and none into no extra character. `n` bytes become
`ceil(8 * n / 11)` characters. radixly's encoder matches the reference
implementation byte for byte on qntm's published test vectors. The decoder
is deliberately stricter than qntm's: a final character that carries no
payload bits is rejected rather than ignored, so one payload has exactly one
accepted spelling.

## When to use it

100 code points hold 137 bytes, where base64 holds 75. Its niche is a
channel that counts characters but treats the high end of the BMP or the
supplementary planes as expensive or unwelcome: base2048 never leaves the
first 4,352 code points. The output reads as a jumble of letters from a
dozen scripts rather than a wall of ideographs, which some channels and
some readers prefer.

The alphabet was picked from assigned, non-combining code points, all stable
under every Unicode normalization form, with no whitespace, control,
punctuation or symbol characters. Because it dips into ASCII, a short
payload can encode to a plain string: `b"\x00"` is `"F"`.

It does not save bytes: as UTF-8 most characters cost two or three. If your
channel counts bytes, base64 or raw binary is the better choice; if it
counts code points and accepts all of the BMP, {doc}`base32768` carries more.

## Truncation behavior

What happens when an encoded string loses characters at its end and you
decode what is left?

base2048 carries no length and no checksum, so the decoder cannot tell a
string is incomplete. It only checks that the last character ends in padding
bits that are all ones. After `k` characters the string holds `11 * k` bits;
the whole bytes are kept and the remaining `11 * k mod 8` bits have to look
like padding. When that remainder is 0 (every eighth cut) the shortened
string is always valid and decodes to a prefix of the payload. Otherwise
random data passes with probability one in 2^remainder. Measured over random
payloads and every cut position, about 23% of truncated strings decode
without an error, every one of them to a prefix; the rest raise
{class}`~radixly.DecodeError` at the last character.

```python
from radixly import base2048

payload = bytes(range(20))
text = base2048.encode(payload)            # 15 characters
base2048.decode(text[:8]) == payload[:11]  # True: 88 bits, no padding to check
```

If you need to know whether a string arrived whole, carry a length or
checksum alongside it, or use {doc}`uro14`, whose length prefix rejects every
truncation below its 16,384-byte window.
