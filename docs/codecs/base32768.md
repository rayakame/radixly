# base32768

15 bits per character from 32,768 BMP code points, decoded strictly and
canonically.

base32768 is [qntm's](https://github.com/qntm/base32768) answer to a simple
question: if a channel counts *characters* instead of bytes, how much can you
fit into each one? Base64 spends a whole character on 6 bits. base32768 picks
an alphabet of 32,768 code points, so every character carries 15 bits, and a
final short character from a second alphabet of 128 carries the last 7 when
the payload does not divide evenly. `n` bytes become `ceil(8 * n / 15)`
characters, nothing more, nothing less.

radixly implements the specification exactly. Its encoder is byte for byte
identical to the reference implementation on qntm's published test vectors,
and its decoder is strict: one payload has exactly one accepted spelling.

## When to use it

It is a dense codec. 100 code points hold 187 bytes, where base64 would hold
75. That is the case it was designed for: anything that limits you by
character count, such as a form field, an identifier with a length cap, or a
filename.

The alphabet is the other half of the argument. qntm chose the 32,768
characters carefully: no whitespace, no control or format characters, no
combining marks, no surrogates, nothing unassigned or private, and every
character is stable under all four Unicode normalization forms. In practice
the text survives being pasted into a chat message, stored in a database
column, or run through a framework that normalizes its input. It looks like
a wall of CJK, Hangul and other scripts, but it is ordinary, well-behaved
text.

One thing it is not good at: saving bytes. Encoded as UTF-8 each character
costs three bytes, so if your channel counts bytes rather than characters,
base64 or plain binary is the better choice.

## Truncation behavior

Truncation means the encoded string loses characters at its end. A field
limit cut it, someone copied only part of it, a message got capped. What
happens when you decode what is left?

base32768 carries no length and no checksum, so the decoder cannot know a
string is incomplete. It checks the one thing it can: the last character has
to end in padding bits that are all ones. Whether a shortened string passes
that check depends on where the cut landed. After `k` characters the string
holds `15 * k` bits. The decoder keeps the whole bytes and expects the
remaining `15 * k mod 8` bits to be padding:

- When that remainder is 0 (every eighth cut position), there is no padding
  to check and the shortened string is always valid. It decodes, without an
  error, to the first `15 * k / 8` bytes of the original payload.
- Otherwise those leftover bits are payload bits that merely have to look
  like padding. With random data that happens with probability one in
  2^remainder: one in two for a single bit, one in 128 for seven.

Averaged over all cut positions on random data, about one in four truncated
strings decodes without an error and returns a prefix of the original bytes.
The other three raise {class}`~radixly.DecodeError` pointing at the last
character.

A concrete case. Twenty bytes encode to eleven characters; cut the text down
to eight and you have 120 bits, which is exactly fifteen bytes and no
padding at all:

```python
from radixly import base32768

payload = bytes(range(20))
text = base32768.encode(payload)            # 11 characters
base32768.decode(text[:8]) == payload[:15]  # True, and no error raised
```

If it matters to you whether a string arrived whole, carry the length or a
checksum alongside it, or use {doc}`uro14`, whose length prefix rejects every
truncation below its 16,384-byte window.
