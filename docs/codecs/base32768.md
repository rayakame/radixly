# base32768

15 bits per character from 32,768 BMP code points, decoded strictly and
canonically.

[qntm's base32768](https://github.com/qntm/base32768) starts from a simple
question: if a channel counts characters instead of bytes, how much fits into
each one? Base64 spends a character on 6 bits. base32768 uses an alphabet of
32,768 code points, so every character carries 15 bits. A leftover of 1 to 7
bits at the end goes into a short character from a second alphabet of 128, a
leftover of 8 to 14 into a padded 15-bit character, and none into no extra
character. `n` bytes become `ceil(8 * n / 15)` characters. radixly's encoder matches the reference
implementation byte for byte on qntm's published test vectors. The decoder
is deliberately stricter than qntm's: a final character that carries no
payload bits is rejected rather than ignored, so one payload has exactly one
accepted spelling.

## When to use it

100 code points hold 187 bytes, where base64 holds 75. That is the case it
was designed for: anything that limits you by character count, such as a
form field, a capped identifier, or a filename.

The alphabet is the other half of the argument. qntm picked characters with
no whitespace, no control or format characters, no combining marks, no
surrogates, nothing unassigned, all stable under every Unicode normalization
form. The text looks like a wall of CJK and Hangul, but it survives chat
messages, database columns and normalizing frameworks unchanged.

It does not save bytes: as UTF-8 each character costs three. If your channel
counts bytes, base64 or raw binary is the better choice.

## Truncation behavior

What happens when an encoded string loses characters at its end and you
decode what is left?

base32768 carries no length and no checksum, so the decoder cannot tell a
string is incomplete. It only checks that the last character ends in padding
bits that are all ones. After `k` characters the string holds `15 * k` bits;
the whole bytes are kept and the remaining `15 * k mod 8` bits have to look
like padding. When that remainder is 0 (every eighth cut) the shortened
string is always valid and decodes to a prefix of the payload. Otherwise
random data passes with probability one in 2^remainder. Averaged over all cut
positions, about one in four truncated strings decodes without an error; the
rest raise {class}`~radixly.DecodeError` at the last character.

```python
from radixly import base32768

payload = bytes(range(20))
text = base32768.encode(payload)            # 11 characters
base32768.decode(text[:8]) == payload[:15]  # True: 120 bits, no padding to check
```

If you need to know whether a string arrived whole, carry a length or
checksum alongside it, or use {doc}`uro14`, whose length prefix rejects every
truncation below its 16,384-byte window.
